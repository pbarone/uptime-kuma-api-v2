# Coding standards

## Style

- Follow PEP 8; match the surrounding code (4-space indent, snake_case).
- Public methods have type hints and a Sphinx-style docstring (see below).
- Validate inputs and raise the library's own exceptions
  (`UptimeKumaException` / `Timeout`), not raw third-party ones, so callers can
  catch a single hierarchy. Range/enum validation belongs near the top of the
  method (see `_build_monitor_data`).
- Prefer small, targeted changes. Don't refactor unrelated code alongside a fix.

## Before writing code

Adapted from [ponytail](https://github.com/DietrichGebert/ponytail) by
@DietrichGebert (MIT), trimmed to this project's constraints. The "brevity does
not license" guards below are where it was adjusted rather than copied — three
of its rules work against a library whose backward compatibility is a contract.

The best code is the code never written. This runs *after* you understand the
problem — read the task, trace the real flow end to end — not instead of it.
Then stop at the first rung that holds:

1. Does this need to exist at all? (YAGNI. See the API-change policy below: new
   *features* are a deliberate decision, not a default.)
2. Is it already in this codebase? Reuse the helper or pattern that's here.
3. Does the standard library do it? Use it.
4. **Does the Uptime Kuma server already do it?** This library's analogue of
   "use the platform" — e.g. the server applies its own default notifications,
   so we don't reimplement that. Confirm against the server's own source and
   tags, never a secondary summary; a wrong answer here becomes a wrong version
   gate.
5. Does an already-installed dependency solve it? Use it.
6. Only then: write the minimum code that works.

Boring over clever. No abstractions, boilerplate, or configurability nobody
asked for. The shortest working diff wins — but only once you understand the
problem, because the smallest change in the wrong place is a second bug rather
than a small fix.

Three things brevity does **not** license here, each because it has already
cost this repo something:

- **Deleting what looks unused.** The pre-1.22 payload path and the dual
  `incident`/`incidents` return keys both read as dead weight and are both
  load-bearing. Deletion is governed by the backward-compatibility policy
  below, not by diff size. Packaging has its own instance of this — the
  `MANIFEST.in` `prune`/`global-exclude` lines — kept in tech steering, where
  the surrounding build context is; don't copy it back here.
- **Touching fewer files than the change needs.** A new public class
  legitimately touches `__init__.py`, `docs/api.rst`, a `MonitorBuilder` setter
  and `CHANGELOG.md` (see "Keep in sync" below). Skipping `docs/api.rst` fails
  silently — autodoc simply omits the class, with no error anywhere.
- **Skipping the test.** What a change needs is set by the testing steering:
  the pytest v2 unit suite, mocked version and transport, proven to fail
  against the unfixed code, and both a v1 and a v2 version wherever behavior is
  gated. A one-line version gate is precisely the change that needs both paths
  covered, not the one small enough to skip.

If a deliberate simplification cuts a real corner with a known ceiling, mark it
with a `ponytail:` comment naming the ceiling and the upgrade path, so the next
reader knows it was a choice rather than an oversight.

## Docstrings (drive the public docs)

The API reference on Read the Docs is generated by Sphinx autodoc from
docstrings, so docstrings ARE the documentation. Keep the existing format:
`:param type name:` lines, `:return:`, `:rtype:`, `:raises:`, and a runnable
`Example::` block. If a docstring contains backslashes (e.g. `\*`), make it a
raw string (`r"""`) to avoid a `SyntaxWarning` on Python 3.12+.

## Backward-compatibility and API-change policy

The public API (anything exported from `__init__.py`, and the signatures/return
shapes of public methods) is a contract. Before changing public behavior:

1. **Never break Uptime Kuma v1.x.** Gate server-version-specific behavior
   behind `parse_version(self.version)`. New fields are added inside a version
   check, not unconditionally.
2. **Additive over breaking.** Prefer new optional parameters (default `None`)
   and new return keys over changing or removing existing ones. When a server
   renames a field across versions, return *both* the old and new keys where
   feasible (see the `incident`/`incidents` handling) so existing callers keep
   working.
3. **Don't casually add public API surface.** Each new public method/parameter
   is a permanent maintenance obligation. New *features* (vs bug fixes) are a
   deliberate decision, not a default; decline scope creep.
4. **A genuine breaking change** requires a major version bump and a
   `BREAKING CHANGE:` note — it is a last resort, not a convenience.
5. **Record judgment calls.** Behavioral decisions (e.g. how an unparseable
   server version is treated, whether the server applies its own default
   notifications) should be documented in the changelog and, if far-reaching,
   noted for consistency in future changes.

## Fixing bugs

- **Reproduce before fixing.** Issue titles in this ecosystem frequently
  misdescribe the real defect; confirm the actual cause in code first.
- **A report names a symptom, not a location.** Trace the flow end to end before
  choosing where to fix, and fix the root cause.
- **Fix the shared function once.** Grep every caller of the function you're
  about to touch. Most public methods funnel through shared helpers
  (`_build_monitor_data` and friends), so one guard in the helper is both a
  smaller diff than one guard per caller and the only version that also fixes
  the sibling callers nobody filed an issue about.
- **Expect adjacent bugs.** Fixing one thing here has repeatedly surfaced
  nearby unreported ones — look around the fix.
- Every bug fix ships with a regression test (see testing steering).

## Keep in sync when adding public API

Export in `__init__.py`, add to `docs/api.rst` (autodoc won't pick it up
otherwise), add a `MonitorBuilder` setter if it's a monitor field, and add a
`CHANGELOG.md` entry.
