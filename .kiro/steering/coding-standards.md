# Coding standards

## Style

- Follow PEP 8; match the surrounding code (4-space indent, snake_case).
- Public methods have type hints and a Sphinx-style docstring (see below).
- Validate inputs and raise the library's own exceptions
  (`UptimeKumaException` / `Timeout`), not raw third-party ones, so callers can
  catch a single hierarchy. Range/enum validation belongs near the top of the
  method (see `_build_monitor_data`).
- Prefer small, targeted changes. Don't refactor unrelated code alongside a fix.

## Docstrings (drive the public docs)

The API reference on Read the Docs is generated by Sphinx autodoc from
docstrings, so docstrings ARE the documentation. Keep the existing format:
`:param type name:` lines, `:return:`, `:rtype:`, `:raises:`, and a runnable
`Example::` block. If a docstring contains backslashes (e.g. `\*`), make it a
raw string (`r"""`) to avoid a `SyntaxWarning` on Python 3.12+.

## Backward-compatibility and API-change policy

The public API (anything exported from `__init__.py`, and the signatures/return
shapes of public methods) is a contract. Before changing public behavior:

1. **Never break Uptime Kuma v1.x.** Gate server-version-specific behavior
   behind `parse_version(self.version)`. New fields are added inside a version
   check, not unconditionally.
2. **Additive over breaking.** Prefer new optional parameters (default `None`)
   and new return keys over changing or removing existing ones. When a server
   renames a field across versions, return *both* the old and new keys where
   feasible (see the `incident`/`incidents` handling) so existing callers keep
   working.
3. **Don't casually add public API surface.** Each new public method/parameter
   is a permanent maintenance obligation. New *features* (vs bug fixes) are a
   deliberate decision, not a default; decline scope creep.
4. **A genuine breaking change** requires a major version bump and a
   `BREAKING CHANGE:` note — it is a last resort, not a convenience.
5. **Record judgment calls.** Behavioral decisions (e.g. how an unparseable
   server version is treated, whether the server applies its own default
   notifications) should be documented in the changelog and, if far-reaching,
   noted for consistency in future changes.

## Fixing bugs

- **Reproduce before fixing.** Issue titles in this ecosystem frequently
  misdescribe the real defect; confirm the actual cause in code first.
- **Expect adjacent bugs.** Fixing one thing here has repeatedly surfaced
  nearby unreported ones — look around the fix.
- Every bug fix ships with a regression test (see testing steering).

## Keep in sync when adding public API

Export in `__init__.py`, add to `docs/api.rst` (autodoc won't pick it up
otherwise), add a `MonitorBuilder` setter if it's a monitor field, and add a
`CHANGELOG.md` entry.
